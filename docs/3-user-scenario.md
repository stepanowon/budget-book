## 1. 개요

### 1.1 목적

이 문서는 공동 가계부 서비스의 실제 사용 흐름을 페르소나 기반으로 구체화하여, 개발·QA·기획 팀이 공통된 사용자 관점을 갖도록 한다. 각 시나리오는 도메인 정의서(1-domain-definition.md)의 비즈니스 규칙(BR), 데이터 규칙(DR), 범위 규칙(SC)을 직접 참조하며, PRD(2-prd.md)의 기능 요구사항(FR)과 연계된 수용 기준을 제공한다.

### 1.2 작성 원칙

- **페르소나 기반**: 각 시나리오는 PRD에서 정의한 3개 페르소나(P-01, P-02, P-03)의 실제 상황과 니즈를 반영한다.
- **도메인 규칙 준수**: 모든 흐름은 도메인 정의서의 규칙 ID를 명시적으로 참조한다.
- **연속성**: 같은 페르소나의 시나리오는 앞 시나리오의 결과를 다음 시나리오의 선행 조건으로 활용한다.
- **현실감**: 구체적인 금액, 날짜, 멤버 수를 사용하여 실제 사용 상황을 재현한다.
- **예외 포함**: 정상 흐름뿐만 아니라 에러 케이스와 대안 흐름을 포함한다.

### 1.3 시나리오 ID 체계

```
SC-{페르소나코드}-{번호}

페르소나코드:
  P01 — 김지수 (여행 총무)
  P02 — 박민준 (가족 살림 담당)
  P03 — 이수연 (모임 총무)
  CMN — 공통 (페르소나 무관)

예시: SC-P01-01 (김지수의 첫 번째 시나리오)
```

## 3. P-01 김지수 — 여행 총무 시나리오

> 페르소나: 김지수 (28세, 직장인), 기술 친숙도 높음, 스마트폰(iOS) 사용
> 상황: 친구 4명과 함께 2026-07-18(토) ~ 2026-07-21(화) 3박 4일 제주도 여행을 계획 중. 김지수가 여행 총무를 맡아 그룹을 생성하고 정산까지 처리한다.

---

### SC-P01-01. 제주도 여행 그룹 생성 및 멤버 초대

**목표:** 김지수가 제주도 여행 기간에 한정된 그룹을 생성하고, 동행자 4명(이호준, 최서아, 장민혁, 윤지은)을 초대하여 총 5명의 그룹을 구성한다.

**선행 조건:**
- 김지수는 서비스에 가입된 `active` 상태의 사용자다. (`username: jisoo_k`)
- 초대 대상 4명 모두 서비스에 가입된 `active` 상태의 사용자다.
  - 이호준: `username: hojun_lee`
  - 최서아: `username: seoa_choi`
  - 장민혁: `username: minhyuk_jang`
  - 윤지은: `username: jieun_yoon`

**주요 흐름:**

1. 김지수가 서비스에 로그인한다.
2. "그룹 만들기"를 선택하여 그룹 생성 화면에 진입한다.
3. 다음 정보를 입력하고 생성을 완료한다.
   - 그룹 이름: `제주도 여행 2026여름`
   - 그룹 타입: `LIMITED` (기간 한정)
   - 시작일: `2026-07-18`
   - 종료일: `2026-07-21`
4. 시스템이 그룹을 생성하고, 김지수를 해당 그룹의 `MANAGER`로 자동 등록한다. (`role = MANAGER`, `joined_at = 생성 시각`)
5. 김지수가 멤버 초대 화면으로 이동하여 `hojun_lee`를 검색하고 초대를 발송한다.
   - 시스템이 `status = PENDING`, `expires_at = 발송 시각 + 7일`인 Invitation 레코드를 생성한다.
6. 동일한 방법으로 `seoa_choi`, `minhyuk_jang`, `jieun_yoon`에게 순차적으로 초대를 발송한다.
7. 4명 모두 초대를 수락하여 그룹에 합류한다. (SC-CMN-01 참조)
8. 최종적으로 그룹 멤버는 총 5명 (MANAGER 1명 + MEMBER 4명)이 된다.

**대안 흐름 / 예외 처리:**

- **[종료일 누락]** `LIMITED` 타입 선택 후 종료일을 입력하지 않고 생성 시도 시: 시스템이 422 에러를 반환하며 "기간 한정 그룹은 종료일 입력이 필수입니다" 메시지를 표시한다. (DR-03)
- **[종료일 오류]** 종료일(`2026-07-17`)이 시작일(`2026-07-18`)보다 이전으로 입력된 경우: 시스템이 422 에러를 반환한다. (DR-03)
- **[중복 초대]** `hojun_lee`에게 PENDING 초대가 이미 존재하는 상태에서 재초대 시도 시: 시스템이 409 에러를 반환한다. (도메인 3.4, FR-I05)
- **[이미 멤버인 사용자 초대]** 그룹에 이미 합류한 멤버를 초대하려는 경우: 시스템이 409 에러를 반환한다. (BR-03)

**참조 규칙:** BR-02, BR-03, DR-03, FR-G01, FR-G02, FR-I01, FR-I02, FR-I05

### SC-P01-02. 여행 중 지출 입력 (균등 분배 N빵)

**목표:** 여행 첫날, 김지수가 대표로 결제한 공항 리무진 버스 요금과 저녁 식사 비용을 균등 분배 방식으로 입력한다.

**선행 조건:**
- SC-P01-01 완료: `제주도 여행 2026여름` 그룹에 5명이 활성 멤버로 등록되어 있다.
- 김지수(`jisoo_k`)는 해당 그룹의 `MANAGER`다.

**주요 흐름 — 지출 1: 공항 리무진 버스**

1. 김지수가 그룹에 진입하여 "지출 입력"을 선택한다.
2. 다음 정보를 입력한다.
   - 금액: `75,000원` (5명 × 1인당 15,000원)
   - 카테고리: `교통` (SYSTEM 카테고리)
   - 날짜: `2026-07-18`
   - 설명: `공항 리무진 버스 (5인)`
   - 결제자: `jisoo_k` (김지수 본인)
   - 분담 방식: `EQUAL` (균등 분배)
   - 참여자: 전원 5명 선택
3. 시스템이 균등 분배를 계산한다.
   - 75,000 ÷ 5 = 15,000원, 나머지 0원
   - 모든 참여자 1인당 분담금: 15,000원
4. 지출이 저장되고 5개의 ExpenseSplit 레코드가 생성된다.

**주요 흐름 — 지출 2: 첫날 저녁 식사**

1. 김지수가 다시 "지출 입력"을 선택한다.
2. 다음 정보를 입력한다.
   - 금액: `127,000원`
   - 카테고리: `식비` (SYSTEM 카테고리)
   - 날짜: `2026-07-18`
   - 설명: `첫날 저녁 — 흑돼지 식당`
   - 결제자: `jisoo_k` (김지수 본인)
   - 분담 방식: `EQUAL` (균등 분배)
   - 참여자: 전원 5명 선택
3. 시스템이 균등 분배를 계산한다.
   - 127,000 ÷ 5 = 25,400원, 나머지 0원
   - 모든 참여자 1인당 분담금: 25,400원
4. 지출이 저장된다.

**균등 분배 나머지 발생 예시 (BR-05 검증):**

> 다음날 이호준이 편의점 구매비 10,000원을 3명(이호준, 최서아, 장민혁)에 대해 균등 분배로 입력하는 경우:
> - 10,000 ÷ 3 = 3,333원, 나머지 1원
> - 결제자 이호준: 3,334원 (나머지 1원 귀속), 최서아: 3,333원, 장민혁: 3,333원

**대안 흐름 / 예외 처리:**

- **[결제자 분담 제외 시도]** 참여자 선택 화면에서 결제자인 `jisoo_k`를 분담 대상에서 제외하려는 경우: 시스템이 결제자를 자동으로 참여자에 포함시키거나 422 에러를 반환한다. 결제자는 항상 분담 대상에 포함된다. (BR-06, FR-E04)
- **[금액 범위 초과]** 금액을 1,000,000,000원(10억)으로 입력 시: 시스템이 422 에러를 반환한다. (도메인 2.2)

**참조 규칙:** BR-05, BR-06, FR-E01, FR-E02, FR-E04, FR-E05

### SC-P01-03. 결제자가 다른 여러 지출 입력 후 여행 정산 실행

**목표:** 여행 기간 중 각자 결제한 다양한 지출을 입력한 뒤, 여행 종료 후 김지수가 전체 기간에 대한 정산을 실행한다.

**선행 조건:**
- SC-P01-02 완료: 일부 지출이 이미 입력되어 있다.
- 여행 기간(2026-07-18 ~ 2026-07-21) 동안 멤버들이 추가 지출을 입력한 상태다.
- 입력된 주요 지출 내역 (결제자 다양):

| 날짜 | 설명 | 금액 | 결제자 | 분담 방식 | 참여자 |
|------|------|------|-------|---------|-------|
| 07-18 | 공항 리무진 버스 | 75,000원 | 김지수 | EQUAL | 전원 5명 |
| 07-18 | 첫날 저녁 — 흑돼지 식당 | 127,000원 | 김지수 | EQUAL | 전원 5명 |
| 07-19 | 숙소 2박 (1일차) | 350,000원 | 이호준 | EQUAL | 전원 5명 |
| 07-19 | 성산일출봉 입장료 | 25,000원 | 최서아 | EQUAL | 전원 5명 |
| 07-20 | 렌터카 | 180,000원 | 장민혁 | EQUAL | 전원 5명 |
| 07-20 | 점심 — 해물뚝배기 | 63,000원 | 윤지은 | EQUAL | 전원 5명 |
| 07-21 | 기념품 쇼핑 | 45,000원 | 김지수 | EQUAL | 전원 5명 |

- 총 지출: 865,000원

**주요 흐름:**

1. 여행 마지막 날(2026-07-21), 김지수가 그룹 화면에서 "정산 실행"을 선택한다.
2. 정산 기간을 입력한다.
   - 시작일: `2026-07-18`
   - 종료일: `2026-07-21`
3. 시스템이 해당 기간 내 모든 지출의 ExpenseSplit을 멤버별로 합산한다.

**정산 계산 결과 (균등 분배 865,000원 ÷ 5명):**

| 멤버 | total_paid (결제액) | total_share (분담액) | balance (차액) |
|-----|-------------------|--------------------|--------------:|
| 김지수 | 247,000원 | 173,000원 | +74,000원 (받을 금액) |
| 이호준 | 350,000원 | 173,000원 | +177,000원 (받을 금액) |
| 최서아 | 25,000원 | 173,000원 | -148,000원 (내야 할 금액) |
| 장민혁 | 180,000원 | 173,000원 | +7,000원 (받을 금액) |
| 윤지은 | 63,000원 | 173,000원 | -110,000원 (내야 할 금액) |

> 865,000원 ÷ 5 = 173,000원, 나머지 0원. 각 멤버의 1인 분담액 = 173,000원.

4. "정산 실행" 버튼을 눌러 정산을 확정한다.
5. 시스템이 Settlement 레코드와 5개의 SettlementDetail 레코드를 생성한다.
6. 시스템이 그룹 전 멤버(5명)에게 정산 내역 요약이 담긴 인앱 메시지를 자동 발송한다. (BR-08)

### SC-CMN-01. 초대 수락/거절 흐름

**목표:** 그룹 MANAGER로부터 초대를 받은 사용자가 수락 또는 거절하는 흐름을 정의한다. 초대 만료 케이스도 포함한다.

**선행 조건:**
- MANAGER가 대상 사용자에게 초대(`status = PENDING`)를 발송한 상태다.
- 대상 사용자는 `active` 상태다.

**주요 흐름 — 수락:**

1. 초대받은 사용자가 서비스에 로그인하면 초대 알림을 확인할 수 있다.
2. 초대 목록에서 해당 그룹 초대를 선택하고 "수락"을 클릭한다.
3. 시스템이 Invitation `status = ACCEPTED`로 갱신하고, `responded_at`을 기록한다.
4. 시스템이 해당 사용자를 대상 그룹의 `MEMBER`로 즉시 추가한다.
   - `GroupMember` 레코드 생성: `role = MEMBER`, `joined_at = 수락 시각`
5. 사용자가 그룹에 입장하여 기존 지출 내역을 조회할 수 있다.

**주요 흐름 — 거절:**

1. 초대받은 사용자가 초대 목록에서 해당 그룹 초대를 선택하고 "거절"을 클릭한다.
2. 시스템이 Invitation `status = DECLINED`로 갱신하고, `responded_at`을 기록한다.
3. 사용자는 해당 그룹에 합류하지 않는다.
4. MANAGER는 거절 이후 동일 사용자에게 재초대를 발송할 수 있다. (PENDING 초대가 없는 상태이므로 중복 초대 제한에 해당하지 않음)

**주요 흐름 — 만료:**

1. 초대 발송 후 7일이 경과한 경우.
2. 배치 프로세스가 1시간 이내에 실행되어 `status = EXPIRED`로 전환한다. (FR-I02, AC-I5)
3. 만료된 초대는 수락/거절 불가 상태가 된다.
4. MANAGER가 재초대를 발송할 수 있다.

**대안 흐름 / 예외 처리:**

- **[만료된 초대 수락 시도]** 사용자가 만료된 초대를 수락하려는 경우: 시스템이 에러를 반환하고 "초대가 만료되었습니다" 메시지를 표시한다.

**참조 규칙:** BR-03, FR-I03, FR-I04, FR-I05

### SC-CMN-02. MANAGER 탈퇴 시 권한 이양

**목표:** 그룹의 유일한 MANAGER가 서비스를 탈퇴할 때, 권한이 자동으로 최선임 활성 MEMBER에게 이양되거나 활성 멤버가 없을 경우 그룹이 비활성화되는 흐름을 정의한다.

**선행 조건:**
- 대상 그룹에 MANAGER 1명과 복수의 MEMBER가 활성 상태로 존재한다.
- 그룹 멤버 및 `joined_at` 정보:
  - MANAGER A: `joined_at = 2026-01-01T09:00:00Z`
  - MEMBER B: `joined_at = 2026-01-05T10:00:00Z`
  - MEMBER C: `joined_at = 2026-02-10T14:00:00Z`

**주요 흐름 — 활성 MEMBER가 있는 경우:**

1. MANAGER A가 서비스 탈퇴를 요청한다. (SC-CMN-03 참조)
2. 시스템이 MANAGER A의 `status = inactive`로 처리하기 전에 권한 이양 대상을 탐색한다.
3. 탐색 조건: 해당 그룹에서 `User.status = active`이며 `GroupMember` 레코드가 존재하는 멤버 중 `joined_at` 가장 이른 순서.
   - MEMBER B (`joined_at = 2026-01-05`)가 MEMBER C보다 먼저 가입했으므로 MEMBER B를 선택한다.
4. 시스템이 MEMBER B의 `role = MANAGER`로 갱신한다. (BR-13)
5. MANAGER A의 탈퇴가 완료된다.
6. MEMBER B는 이후 해당 그룹의 MANAGER 권한으로 그룹 관리 기능을 수행할 수 있다.

**주요 흐름 — 활성 MEMBER가 없는 경우:**

1. 그룹에 MANAGER A만 존재하고 활성 MEMBER가 없는 상태에서 MANAGER A가 탈퇴를 요청한다.
2. 시스템이 이양 대상을 탐색하지만 조건에 맞는 활성 멤버가 없음을 확인한다.
3. 시스템이 MANAGER A의 탈퇴를 처리하고, 해당 그룹을 `status = inactive`로 전환한다. (BR-14)
4. 비활성화된 그룹은 이후 조회만 가능하고 신규 지출 입력·정산 실행이 불가하다.

**참조 규칙:** BR-12, BR-13, BR-14, FR-G05, FR-G06

### SC-CMN-03. 회원 탈퇴 처리

**목표:** 서비스 사용자가 탈퇴를 요청했을 때 시스템이 처리하는 흐름을 정의한다. 물리 삭제 없이 `inactive` 상태로 전환하며 기존 데이터를 보존한다.

**선행 조건:**
- 탈퇴 요청 사용자는 `active` 상태다.
- 해당 사용자는 1개 이상의 그룹에 멤버로 소속되어 있다.

**주요 흐름:**

1. 사용자가 계정 설정 > "회원 탈퇴"를 선택한다.
2. 시스템이 탈퇴 확인 안내를 표시한다.
   - "탈퇴 후 계정 정보는 복구되지 않습니다. 그룹 내 지출 기록은 유지됩니다."
3. 사용자가 탈퇴를 최종 확인한다.
4. 시스템이 다음 처리를 순차적으로 실행한다.
   a. 해당 사용자가 MANAGER인 그룹에 대해 SC-CMN-02의 권한 이양 로직을 실행한다. (BR-13)
   b. `User.status = inactive`로 전환 (물리 삭제 없음). (BR-12)
   c. 해당 사용자의 모든 Refresh Token을 즉시 삭제하여 토큰 재발급을 차단한다. (FR-U04) 이미 발급된 Access Token은 만료(최대 1시간)까지 유효할 수 있다.
5. 탈퇴 완료 후 사용자는 자동 로그아웃된다.
6. 기존 지출 기록, ExpenseSplit, SettlementDetail은 모두 원본 그대로 보존된다. (BR-12, FR-U05)

**탈퇴 후 데이터 가시성:**
- 탈퇴 사용자의 지출 기록은 그룹 멤버들에게 계속 표시된다. (현재 구현에서는 현재 멤버 목록에 없는 결제자가 사용자 식별자(UUID)로 표시되며, 표시명 처리는 미구현)
- 탈퇴 사용자가 결제자 또는 분담자로 등록된 기존 정산 결과는 변경되지 않는다.

**대안 흐름 / 예외 처리:**

- **[탈퇴 후 로그인 시도]** 탈퇴 완료된 계정(`inactive`)으로 로그인 시도 시: 시스템이 401 에러를 반환한다. (AC-U4)
