# PRD — 공동 가계부 서비스

**버전:** 1.1  
**작성일:** 2026-06-17  
**참조 문서:** `docs/1-domain-definition.md`

## 1. 제품 개요

### 1.1 배경 및 목적

기존 가계부 앱은 단일 사용자만 지출 내역을 입력할 수 있어, 여러 사람이 함께 소비하는 상황(여행, 가족 생활비, 정기 모임 등)에서 한 사람에게 기록 부담이 집중된다. 또한 공동 지출 후 누가 얼마를 냈는지 정산하는 과정이 수기 계산이나 메신저 주고받기에 의존해 번거롭고 오류가 발생하기 쉽다.

이 서비스는 **그룹 단위의 공동 가계부**를 제공하여, 여러 멤버가 함께 지출을 기록하고 자동으로 정산 금액을 계산할 수 있도록 한다.

### 1.2 핵심 가치 제안

- 그룹 멤버 누구나 지출을 입력할 수 있어 기록 부담을 분산
- 정산 금액을 자동 계산하여 수기 계산 오류 제거
- 여행(기간 한정)과 가족/모임(상시) 두 가지 그룹 유형으로 다양한 공동 지출 상황을 지원
- 카테고리별 지출 통계로 그룹 소비 패턴 파악

## 2. 목표 사용자 페르소나

### 페르소나 1 — 여행 지출 정산이 귀찮은 직장인

- **이름/나이/직업:** 이지민, 29세, 마케터
- **주요 사용 시나리오:** 친구 4명과 제주도 3박 4일 여행을 계획 중. 숙소·교통·식비를 각자 번갈아 결제하는데, 여행 후 각자가 낸 금액을 집계해 정산하는 과정이 매번 카카오톡과 엑셀을 오가며 복잡하다.
- **가장 중요하게 생각하는 것:** 정산 계산의 정확성. 여행 중 영수증을 잊어버리기 전에 빠르게 입력할 수 있는 편의성.
- **불편해하는 것:** 여행 끝난 뒤 누군가가 전체 지출을 정리해줘야 한다는 부담감. "내가 얼마 받아야 하지?"를 매번 직접 계산해야 하는 번거로움.

### 페르소나 2 — 가족 생활비를 함께 관리하는 맞벌이 부부

- **이름/나이/직업:** 김태우, 38세, 회사원 (배우자와 함께 사용)
- **주요 사용 시나리오:** 부부가 각자 카드로 생활비를 지출하는데, 월말에 누가 더 썼는지 확인하고 균형을 맞추고 싶다. 식비·공과금·육아비 등 항목별로 얼마나 썼는지 파악하고 싶다.
- **가장 중요하게 생각하는 것:** 번거롭지 않은 입력 (지출 발생 즉시 모바일로 빠르게 기록). 카테고리별 월간 지출 요약.
- **불편해하는 것:** 지출 기록이 어느 한 명에게 집중되는 것. 월말에 카드 명세서 여러 개를 합산해 계산해야 하는 것.

## 3. 기능 요구사항

### 3.1 MVP (1차 출시) 포함 기능

#### F-01. 사용자 인증

| ID | 요구사항 |
|----|---------|
| F-01-1 | 이메일 + 비밀번호로 회원가입할 수 있다. 비밀번호는 최소 8자 이상, 영문+숫자 조합을 필수로 한다. |
| F-01-2 | 회원가입 시 사용자명(username)을 입력하며, 사용자명은 서비스 내 유일해야 한다. |
| F-01-3 | 이메일 + 비밀번호로 로그인할 수 있다. |
| F-01-4 | JWT 기반 인증(Access Token + Refresh Token)을 사용한다. Access Token 만료: 1시간, Refresh Token 만료: 30일. |
| F-01-5 | Access Token 만료 시 클라이언트는 Refresh Token으로 자동 갱신을 시도한다. Refresh Token도 만료된 경우 강제 로그아웃 처리한다. |
| F-01-6 | 로그아웃 시 Refresh Token을 무효화한다. |
| F-01-7 | 회원 탈퇴 시 이메일·사용자명 등 개인정보는 즉시 삭제되고, 지출·정산 기록에 남은 이름은 `(탈퇴한 사용자)`로 익명화 후 영구 보존된다. |
| F-01-8 | 비밀번호를 분실한 경우 이메일로 재설정 링크를 발송받아 변경할 수 있다. 재설정 링크의 유효 시간은 1시간이며, 사용 후 즉시 무효화된다. |

#### F-02. 그룹 관리

| ID | 요구사항 |
|----|---------|
| F-02-1 | 사용자는 그룹을 생성할 수 있으며, 생성 시 유형(기간 한정 / 상시)을 선택한다. |
| F-02-2 | 기간 한정 그룹은 시작일과 종료일을 필수로 입력한다. |
| F-02-3 | 상시 그룹은 종료일 없이 생성된다. |
| F-02-4 | 그룹 생성자는 자동으로 그룹 관리자가 된다. |
| F-02-5 | 그룹 관리자는 사용자명으로 다른 사용자를 검색하여 멤버로 초대할 수 있다. |
| F-02-6 | 초대받은 사용자는 인앱 알림에서 수락 또는 거절을 선택한다. 수락 시 그룹 멤버가 된다. |
| F-02-7 | 초대는 발송 후 7일이 경과하면 자동 만료된다. |
| F-02-8 | 다음 경우에는 초대를 발송할 수 없다: ① PENDING 상태의 초대가 이미 존재하는 대상, ② 이미 그룹 멤버인 사용자. 각각 별도 안내 메시지를 표시한다. |
| F-02-9 | 그룹 관리자는 다른 멤버에게 관리자 권한을 부여할 수 있다 (복수 관리자 허용). |
| F-02-10 | 그룹 관리자는 멤버를 강퇴할 수 있다. |
| F-02-11 | 멤버는 스스로 그룹에서 탈퇴할 수 있다. 단, 마지막 관리자는 권한 이전 전까지 탈퇴 불가. |
| F-02-12 | 탈퇴·강퇴된 멤버의 지출 기록은 삭제되지 않으며, 해당 멤버는 `(탈퇴한 사용자)`로 표시된다. |
| F-02-13 | 기간 한정 그룹은 종료일 자정(KST 00:00)에 자동으로 ARCHIVED 상태가 된다. ARCHIVED 후에는 지출 입력이 불가하다. |
| F-02-14 | 관리자는 상시 그룹을 수동으로 비활성화(ARCHIVED)할 수 있다. |
| F-02-15 | 그룹 삭제 기능은 제공하지 않는다. 비활성화(ARCHIVED) 처리만 가능하며, 데이터는 3년간 보존된다. |

#### F-03. 지출 관리

| ID | 요구사항 |
|----|---------|
| F-03-1 | 그룹 멤버는 지출을 입력할 수 있다 (금액, 카테고리, 날짜, 결제자, 참여자, 메모). |
| F-03-2 | 결제자는 그룹 멤버 중에서 선택하며, 입력자와 달라도 된다. |
| F-03-3 | 참여자는 1인 이상 선택해야 하며 결제자를 포함할 수 있다. |
| F-03-4 | 분담액은 `지출 금액 ÷ 참여자 수`를 원 단위로 반올림하여 계산한다. 오차는 결제자가 부담한다. |
| F-03-5 | 기간 한정 그룹에서는 종료일 이후 날짜의 지출을 입력할 수 없다. |
| F-03-6 | 지출 입력자 본인 또는 그룹 관리자만 해당 지출을 수정·삭제할 수 있다. |
| F-03-7 | 모든 그룹 멤버는 그룹 내 전체 지출 내역을 조회할 수 있다. |

#### F-04. 카테고리 관리

| ID | 요구사항 |
|----|---------|
| F-04-1 | 시스템은 기본 카테고리(식비, 교통, 숙박, 쇼핑, 문화/여가, 의료, 기타)를 제공한다. |
| F-04-2 | 그룹 관리자 및 멤버 모두 커스텀 카테고리를 추가할 수 있다. |
| F-04-3 | 커스텀 카테고리의 수정·삭제는 그룹 관리자만 가능하다. |
| F-04-4 | 커스텀 카테고리 삭제 시, 해당 카테고리에 연결된 기존 지출 기록은 보존된다. |

#### F-05. 정산

| ID | 요구사항 |
|----|---------|
| F-05-1 | 상시 그룹은 매월 1일 00:00 (KST, UTC+9)에 이전 월의 지출을 집계하여 정산 내역을 자동 생성한다. |
| F-05-2 | 기간 한정 그룹의 관리자는 수동으로 정산을 실행할 수 있다. 정산 기간(시작일~종료일)은 관리자가 직접 지정하며, 기본값은 "마지막 정산 다음 날~오늘"로 자동 설정된다. 그룹 생성 후 첫 정산의 기본 시작일은 그룹 시작일이다. |
| F-05-3 | 정산 실행(자동/수동) 시 모든 멤버에게 인앱 알림을 전송한다. |
| F-05-4 | 알림에는 총 지출액, 개인별 분담액, 송금 대상 및 금액이 포함된다. |
| F-05-5 | 동일 기간(시작일~종료일)에 대해 이미 정산이 존재하면 중복 실행할 수 없다. |
| F-05-6 | 송금 당사자(from_member) 본인만 해당 정산 내역에 정산 완료를 체크할 수 있다. |
| F-05-7 | 정산 히스토리는 영구적으로 조회할 수 있다. |
| F-05-8 | 자동 정산 배치 실패 시, 시스템은 오류를 기록하고 영향받은 그룹의 관리자에게 인앱 알림을 전송한다. 관리자는 수동으로 재실행할 수 있다. |
| F-05-9 | **정산 알고리즘:** 각 멤버의 순 채권채무(총 결제액 - 총 분담액)를 계산한 뒤, 최소 거래 수로 정산이 완료되도록 이체 목록을 생성한다. (채무자가 가장 큰 채권자에게 우선 이체하는 그리디 방식) |

#### F-06. 인앱 알림 (메시지함)

| ID | 요구사항 |
|----|---------|
| F-06-1 | 사용자는 인앱 메시지함에서 수신한 모든 알림을 확인할 수 있다. |
| F-06-2 | 알림 종류: 그룹 초대 요청, 초대 수락/거절 결과, 초대 만료, 정산 내역 생성, 자동 정산 배치 실패 (관리자 수신). |
| F-06-3 | 읽지 않은 알림은 시각적으로 구분 표시된다. |
| F-06-4 | 초대 알림에서 바로 수락/거절을 선택할 수 있다. |

#### F-07. 리포트

| ID | 요구사항 |
|----|---------|
| F-07-1 | 사용자는 기간(시작일~종료일)을 지정하여 카테고리별 지출 비율을 파이 차트로 조회할 수 있다. |
| F-07-2 | 동일한 기간 필터를 적용한 지출 목록을 `.xlsx` 파일로 내보낼 수 있다. |
| F-07-3 | 내보내기 파일 컬럼: 날짜, 카테고리, 금액, 결제자, 참여자, 메모. |

## 5. 비기능 요구사항

### 5.1 성능

| 지표 | 목표값 |
|------|--------|
| 일반 API 응답 시간 (95th percentile) | 500ms 이하 |
| 정산 계산 API 응답 시간 | 2,000ms 이하 |
| 동시 접속 사용자 수 (초기) | 100명 |
| 동시 접속 사용자 수 (확장 목표) | 10,000명 |

### 5.2 가용성

| 지표 | 목표값 |
|------|--------|
| 목표 업타임 | 99.9% (월 다운타임 43분 이내) |
| 정기 점검 | 불허. 무중단 배포 적용 |

> **참고:** 99.99%는 연간 약 52분의 다운타임만 허용하며, 1인 개발·초기 운영 환경에서는 달성이 현실적으로 어렵다. 인프라 성숙 후 99.99%로 상향한다.

### 5.3 보안

| 항목 | 요구사항 |
|------|---------|
| 인증 방식 | JWT (Access Token 만료: 1시간, Refresh Token 만료: 30일) |
| Token 갱신 | Access Token 만료 시 자동 갱신. Refresh Token 만료 시 강제 로그아웃 |
| 비밀번호 저장 | bcrypt 해시 (salt rounds ≥ 12) |
| 비밀번호 정책 | 최소 8자, 영문+숫자 조합 필수 |
| CORS | 허용 오리진을 환경변수로 관리. 프로덕션에서 와일드카드(`*`) 사용 금지 |
| HTTPS | 모든 통신 TLS 1.2 이상 필수 |
| API 인가 | 모든 API 엔드포인트는 JWT 검증 후 그룹 멤버십 확인 |

## 6. 운영 정책

### 6.1 언어 및 통화

| 항목 | MVP | 2차 개발 |
|------|:---:|:-------:|
| 서비스 언어 | 한국어 | 영어 추가 |
| 지원 통화 | 원화(KRW) | 다중 통화 추가 |

### 6.2 데이터 보존 정책

| 상황 | 처리 방식 |
|------|---------|
| 그룹 비활성화(ARCHIVED) 후 데이터 | 3년간 보존 후 삭제 |
| 회원 탈퇴 시 개인정보 (이메일, 사용자명) | 즉시 삭제 |
| 회원 탈퇴 후 지출·정산 기록 | `(탈퇴한 사용자)`로 익명화 후 영구 보존 |

### 6.3 정산 배치 장애 처리

- 상시 그룹 자동 정산 배치(매월 1일 KST) 실패 시 오류 로그를 기록한다.
- 영향받은 그룹의 관리자에게 인앱 알림(BATCH_FAILURE)을 전송한다.
- 관리자는 수동 정산 실행으로 재처리할 수 있다.

## 7. UX 방향성

### 7.1 디자인 원칙

- **Google Material Design** 스타일 참고. 여백이 충분하고 정보가 명확히 구분되는 깔끔한 UI.
- 복잡한 정산 결과도 한눈에 파악할 수 있도록 카드 레이아웃과 숫자 강조 표현 활용.
- 데스크톱과 모바일 동등하게 설계. 모바일에서도 지출 입력이 3탭 이내에 완료되도록 UX 설계.

### 7.2 반응형 레이아웃 기준

| 화면 폭 | 레이아웃 |
|--------|---------|
| ≥ 1024px | 사이드바 + 콘텐츠 2단 레이아웃 |
| < 1024px | 하단 탭바 기반 단일 컬럼 레이아웃 |
